Staffing App: Microsoft Entra, Graph y SharePoint

Qué hace la integración, qué está implementado en el código y qué configuración corporativa falta para que una persona inicie sesión y vea las listas Assignments y Staff.

En esta guía Estado actual Flujo técnico Configuración Entra Permisos y acceso Configuración local Prueba en Docker Diagnóstico Seguridad y límites Solicitud para IT
Resumen: el flujo de aplicación ya está programado, pero no puede iniciar sesión ni leer SharePoint hasta que los registros de aplicación, el consentimiento y los datos del tenant estén configurados. No se deben inventar IDs ni credenciales.

SharePoint configurado en el proyecto: TSA-Operaciones, hostname ts.accenture.com, ruta /sites/TSA-Operaciones. Listas esperadas: Assignments y Staff.

2. Flujo de inicio de sesión y lectura

1. Usuario Pulsa “Iniciar sesión corporativa”.
2. Entra Autentica al usuario y devuelve un token para la API Django.
3. Django Verifica el token y usa OBO para solicitar un token delegado de Graph.
4. Graph Comprueba el permiso delegado de la aplicación y el acceso del usuario al sitio.
5. SharePoint Graph entrega a Django los elementos que el usuario puede leer; React los presenta.

Qué representa cada componente

  • Microsoft Entra ID: autentica la cuenta corporativa, emite tokens y aplica las políticas de la organización.
  • Microsoft Graph: API oficial de Microsoft 365. Django la consulta para localizar el sitio, sus listas y los elementos.
  • SharePoint: contiene las listas y aplica los permisos de lectura de la cuenta.
  • Secreto de la API: permite que Django se autentique como cliente confidencial durante el intercambio OBO; no es la contraseña del usuario y no concede por sí solo acceso a las listas.
El secreto y el token de Graph permanecen en el backend. React recibe un token dirigido a Django; no recibe el secreto ni el token delegado de Graph.

3. Configuración que se necesita en Entra

El diseño actual emplea dos registros de aplicación del mismo tenant. Si la política corporativa exige que IT cree los registros, se le deben solicitar. Si permiten que el equipo de desarrollo los cree, un administrador tendrá que aprobar los permisos que lo requieran.

A. Registro de la API Django (cliente confidencial)

  1. Registro de un solo tenant en el tenant corporativo.
  2. Configurar tokens de acceso v2 (requestedAccessTokenVersion: 2 en el manifiesto).
  3. En Expose an API, configurar el Application ID URI, normalmente api://<API_CLIENT_ID>, y exponer el scope delegado access_as_user.
  4. En permisos de Microsoft Graph, agregar el permiso delegado Sites.Read.All y otorgar consentimiento administrativo según la política del tenant.
  5. Crear una credencial confidencial para OBO. El código actual admite un client secret. Si IT exige certificado o identidad federada, habrá que adaptar la implementación antes de usar esa modalidad.
  6. Registrar el Application (client) ID de la API, el Tenant ID y la credencial para el entorno local.

B. Registro de la aplicación web React (SPA pública)

  1. Registrar una SPA en el mismo tenant.
  2. Agregar una URI de redirección tipo SPA: http://localhost:5173.
  3. Agregar permiso delegado a la API Django: api://<API_CLIENT_ID>/access_as_user.
  4. Registrar el Application (client) ID de la SPA.
Los nombres de menús pueden variar entre el portal y la política corporativa. IT debe confirmar el método de consentimiento permitido y que la versión de token del API sea compatible con la validación del backend.

4. Dos comprobaciones de permiso distintas

  1. Consentimiento de la aplicación: el tenant autoriza a la aplicación API a solicitar el scope delegado de Graph Sites.Read.All. Este permiso puede requerir aprobación administrativa conforme a la política corporativa.
  2. Acceso del usuario a SharePoint: la cuenta que inició sesión debe poder abrir y leer el sitio y las listas correspondientes. El permiso delegado hace que Graph actúe en nombre de esa cuenta; no debe convertir al usuario en alguien con más permisos de los que ya tiene.

Por eso un login satisfactorio no garantiza que la lectura funcione. IT puede aprobar la aplicación y, aun así, un usuario sin acceso al sitio recibirá un error de Graph.

El código solicita https://graph.microsoft.com/.default para el intercambio OBO. En este flujo representa los permisos delegados de Graph configurados y consentidos para la aplicación API; no significa que se esté usando un token app-only.

5. Variables de configuración

Crear un archivo local .env a partir de .env.example. No subir el archivo real a Git ni pegar el secreto en tickets, correo o chat.

Variable Valor que contiene ¿Secreto?
ENTRA_TENANT_ID ID del tenant corporativo. No
ENTRA_API_CLIENT_ID Application/client ID del registro API Django. No
ENTRA_CLIENT_SECRET Campo Value del secreto creado para la API. No usar el campo Secret ID. Sí: confidencial
VITE_ENTRA_CLIENT_ID Application/client ID del registro SPA. No
VITE_ENTRA_TENANT_ID El mismo tenant ID. No
VITE_ENTRA_API_SCOPE api://<API_CLIENT_ID>/access_as_user. No
SHAREPOINT_SITE_HOST ts.accenture.com. No
SHAREPOINT_SITE_PATH /sites/TSA-Operaciones. No
SHAREPOINT_ASSIGNMENTS_LIST_NAME Assignments. No
SHAREPOINT_STAFF_LIST_NAME Staff. No

Importante: hay dos valores llamados “secret”

  • ENTRA_CLIENT_SECRET es la credencial de la API Entra para OBO.
  • DJANGO_SECRET_KEY es una clave interna que Django usa para su seguridad web. No es una credencial de Microsoft.

El frontend utiliza variables con prefijo VITE_; estas quedan incluidas en el bundle público. Solo deben contener IDs y configuración pública, nunca secretos.

6. Cómo arrancar y validar en WSL con Docker

cp .env.example .env
# Completar .env con los datos proporcionados por IT
docker compose up --build --renew-anon-volumes

Abrir http://localhost:5173, iniciar sesión y seleccionar Leer listas de SharePoint.

Comprobaciones técnicas:

docker compose ps
curl http://localhost:8000/api/health/
docker compose exec backend python manage.py test
docker compose exec frontend npm run lint

Endpoints de prueba

  • GET /api/health/: health check del backend, no requiere token de usuario.
  • GET /api/me/: valida el token y devuelve los datos básicos del usuario.
  • GET /api/sharepoint/items/: valida el token, realiza OBO y devuelve ambas listas.

El endpoint de SharePoint y /api/me/ requieren Authorization: Bearer <token-de-la-API>. La interfaz lo solicita con MSAL y lo envía a Django.

7. Diagnóstico de errores

Síntoma Capa probable Qué revisar
La pantalla indica variables VITE faltantes. Configuración frontend/Docker IDs de tenant/SPA y API scope en .env; reiniciar Compose después de cambiarlo.
Entra muestra redirect URI o aplicación inválida. Registro SPA/Entra URI SPA exacta http://localhost:5173, tenant y client ID.
Django responde 401. Token/API Audience/API ID, tenant, issuer, expiración y que el token esté destinado a Django.
Django responde 403 o el intercambio OBO falla. Consentimiento Entra/OBO Scope access_as_user, permiso delegado de Graph, consentimiento y credencial del cliente.
Graph responde acceso denegado. Permiso de aplicación o usuario Consentimiento delegado de Graph y permiso de lectura del usuario sobre el sitio/listas.
Una lista no aparece. SharePoint/configuración de lista Título exacto visible, sitio correcto y que Graph enumere la lista para ese usuario.
503 con variables de Entra faltantes. Configuración backend Variables ENTRA_* en el contenedor Django.

Para ver el mensaje de Microsoft/Graph durante el diagnóstico local: 

docker compose logs -f backend

No publicar logs si contienen tokens, valores de secretos u otros datos corporativos.

8. Seguridad y alcance de esta fase

  • Nunca solicitar ni almacenar la contraseña Microsoft del usuario.
  • Nunca poner ENTRA_CLIENT_SECRET en variables VITE_, React, el bundle o Git.
  • El secreto se crea en el registro API, se copia del campo Value una sola vez y se guarda únicamente en el .env local durante desarrollo.
  • Registrar la expiración y rotar el secreto antes de que venza. Para producción, utilizar el gestor de secretos aprobado por IT; esta versión del código está configurada para client secret.
  • No se implementan todavía paginación completa, escritura, procesamiento de CVs, LLM ni interfaz definitiva.

9. Texto que se puede enviar a IT

Estamos desarrollando una aplicación interna React + Django que debe permitir
iniciar sesión con cuentas corporativas y leer, en nombre del usuario, las
listas Assignments y Staff de:
https://ts.accenture.com/sites/TSA-Operaciones

¿Podéis crear/configurar (o autorizarnos a crear) dos registros de aplicación
del mismo tenant?

1) API Django: single-tenant, tokens v2, exponer scope delegado
   access_as_user, y permitir el flujo OAuth On-Behalf-Of.
2) SPA React: redirect URI de tipo SPA http://localhost:5173 y permiso
   delegado api://<API_CLIENT_ID>/access_as_user.

La API necesita el permiso delegado de Microsoft Graph Sites.Read.All con el
consentimiento que exija la política del tenant. El acceso a SharePoint debe
seguir los permisos del usuario (no necesitamos acceso app-only).

Por favor, proporcionad el Tenant ID y los Application/Client ID de la API y
de la SPA. La API necesita una credencial confidencial para OBO; el código
actual utiliza client secret. Indicad si podemos crearla como propietarios
del registro, o cuál es el procedimiento corporativo seguro para provisionarla.
No enviaremos el secreto por correo o chat.

Si la política no permite Sites.Read.All, IT debe indicar una alternativa delegada de menor alcance compatible con listar el sitio y leer ambas listas. No sustituir por permisos de aplicación amplios sin una decisión explícita de seguridad.
